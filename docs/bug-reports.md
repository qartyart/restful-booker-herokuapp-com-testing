## BUG-01 — POST /auth — неверные учётные данные возвращают 200 OK вместо 401

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Critical — клиент не может отличить успешную авторизацию от неуспешной по коду ответа. Любой потребитель, проверяющий `response.status === 200`, будет считать себя авторизованным с любым паролем.
**Priority:** High

### Предусловия
- Стенд доступен, `GET /ping` отвечает.

### Шаги воспроизведения
1. Отправить `POST https://restful-booker.herokuapp.com/auth` с заголовком `Content-Type: application/json`.
2. Тело запроса: `{"username":"admin","password":"WRONG"}`.
3. Посмотреть код ответа.

### Ожидаемый результат (ОР)
Код `401 Unauthorized`, токен не выдан. Стандартный код для непройденной аутентификации (RFC 9110 §15.5.2).

### Фактический результат (ФР)
Код `200 OK`, тело `{"reason":"Bad credentials"}`. Признак ошибки передан только в теле.

### Вложения
```http
POST /auth HTTP/1.1
Content-Type: application/json

{"username":"admin","password":"WRONG"}

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"reason":"Bad credentials"}
```

Тот же `200 OK` с `{"reason":"Bad credentials"}` возвращается при: неверном логине, обоих неверных полях, отсутствии `username`, отсутствии `password`, пустом теле `{}`, пустых строках в обоих полях, неподходящем `Content-Type`. Для отсутствующих обязательных полей ОР — `400 Bad Request`, для неподходящего `Content-Type` — `415 Unsupported Media Type`.

### Воспроизводимость
100 % — 2 независимых прогона + 8 проверок в коллекции (TC-AUTH-03…TC-AUTH-09, TC-AUTH-11).

## BUG-02 — POST /booking — невалидная дата не отклоняется, а записывается в базу как `0NaN-aN-aN`

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Critical — порча данных. В базу попадает значение, не являющееся датой ни в одном формате; бронь становится непригодной для любой обработки по датам и навсегда выпадает из фильтров.
**Priority:** High

### Предусловия
- Стенд доступен.

### Шаги воспроизведения
1. Отправить `POST /booking` с телом:
   ```json
   {"firstname":"NaNProbe","lastname":"Tester","totalprice":111,"depositpaid":true,
    "bookingdates":{"checkin":"2026-13-45","checkout":"2026-14-50"},"additionalneeds":"x"}
   ```
2. Запомнить `bookingid` из ответа.
3. Отправить `GET /booking/{bookingid}` и посмотреть `bookingdates`.

### Ожидаемый результат (ОР)
Код `400 Bad Request`, бронь не создана. Документация задаёт формат `CCYY-MM-DD`; `2026-13-45` — несуществующая дата.

### Фактический результат (ФР)
Код `200 OK`, бронь создана. При чтении обратно обе даты равны строке `0NaN-aN-aN` — значение записано в базу и сохраняется там.

### Вложения
```http
POST /booking HTTP/1.1
Content-Type: application/json

{"firstname":"NaNProbe","lastname":"Tester","totalprice":111,"depositpaid":true,
 "bookingdates":{"checkin":"notadate","checkout":"garbage"},"additionalneeds":"x"}

HTTP/1.1 200 OK

{"bookingid":3146,"booking":{"firstname":"NaNProbe","lastname":"Tester","totalprice":111,
 "depositpaid":true,"bookingdates":{"checkin":"0NaN-aN-aN","checkout":"0NaN-aN-aN"},
 "additionalneeds":"x"}}
```
```http
GET /booking/3146 HTTP/1.1

HTTP/1.1 200 OK

{"firstname":"NaNProbe","lastname":"Tester","totalprice":111,"depositpaid":true,
 "bookingdates":{"checkin":"0NaN-aN-aN","checkout":"0NaN-aN-aN"},"additionalneeds":"x"}
```

Смежное проявление того же отсутствия валидации: дата `01-01-2026` (формат DD-MM-YYYY) принимается и **молча переинтерпретируется** в `2026-01-01`. Клиент, приславший 1 января в европейском формате, получит бронь на другую дату без единого предупреждения.

### Воспроизводимость
100 % — 2 независимых прогона + 4 проверки в коллекции (TC-CRE-20, TC-CRE-21, TC-CRE-22, TC-GET-02a).

## BUG-03 — GET /booking — фильтр `checkout` инвертирован: возвращает брони с датой выезда РАНЬШЕ заданной

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Critical — фильтр возвращает ровно противоположную выборку. Потребитель, ищущий «брони с выездом не раньше даты X», получает «брони с выездом не позже X» и делает неверные выводы, не получая никакой ошибки.
**Priority:** High

### Предусловия
- Создана бронь с `checkin=2031-06-15`, `checkout=2031-06-20` (id далее — `{id}`).

### Шаги воспроизведения
1. Отправить `GET /booking?checkout=2031-01-01`. Дата выезда брони (`2031-06-20`) **больше** `2031-01-01`.
2. Проверить, есть ли `{id}` в выдаче.
3. Отправить `GET /booking?checkout=2032-01-01`. Дата выезда брони **меньше** `2032-01-01`.
4. Проверить, есть ли `{id}` в выдаче.

### Ожидаемый результат (ОР)
Документация: «Return bookings that have a checkout date greater than or equal to the set checkout date».
Шаг 2 — бронь **в выдаче** (`2031-06-20 >= 2031-01-01`).
Шаг 4 — брони **в выдаче нет** (`2031-06-20 >= 2032-01-01` ложно).

### Фактический результат (ФР)
Шаг 2 — брони в выдаче **нет**.
Шаг 4 — бронь **в выдаче есть**.
Сравнение выполняется в обратную сторону: фактически фильтр отбирает `checkout <= заданной`.

### Вложения
Проверка на срезе из 60 броней: по запросу `GET /booking?checkout=2023-02-19` вернулось 2222 id, среди которых **51 бронь с датой выезда раньше** `2023-02-19` — например, id 8 (`checkout=2022-07-05`), id 11–25 (`checkout=2019-01-01`). Контрольный запрос `GET /booking?checkout=1900-01-01` возвращает `[]`: при корректном `>=` он вернул бы весь список.

### Воспроизводимость
100 % — 2 независимых прогона + 2 проверки в коллекции (TC-LST-14, TC-LST-15).

## BUG-04 — GET /booking — совместное указание `checkin` и `checkout` всегда возвращает пустой массив

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Critical — основной сценарий эндпоинта «найти брони на диапазон дат» не работает ни при каких значениях параметров. Пример из официальной документации возвращает пустой результат.
**Priority:** High

### Предусловия
- Создана бронь с `checkin=2031-06-15`, `checkout=2031-06-20`.

### Шаги воспроизведения
1. Отправить `GET /booking?checkin=2031-06-14&checkout=2031-01-01` — обе документированные границы для этой брони выполняются.
2. Посмотреть тело ответа.
3. Дополнительно отправить пример из документации: `GET /booking?checkin=2014-03-13&checkout=2014-05-21`.

### Ожидаемый результат (ОР)
Шаг 1 — выдача содержит id созданной брони.
Шаг 3 — непустая выдача: пример приведён в документации как рабочий.

### Фактический результат (ФР)
Оба запроса возвращают `200 OK` и пустой массив `[]`.
Причина — сочетание BUG-06 и BUG-03: `checkin` отбирает «строго позже», `checkout` — «не позже», и пересечение этих двух условий по одной и той же шкале дат пусто при любых входных данных.

### Вложения
```http
GET /booking?checkin=2014-03-13&checkout=2014-05-21 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

[]
```
По отдельности те же параметры выдачу дают: `?checkin=2019-08-29` → 13 id, `?checkout=2023-02-19` → 2222 id. Вместе — всегда `[]`.

### Воспроизводимость
100 % — 2 независимых прогона + 2 проверки в коллекции (TC-LST-16, TC-LST-17).

## BUG-06 — GET /booking — фильтр `checkin` исключает бронь с граничной датой

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Major — классическая ошибка «на единицу»: брони, начинающиеся ровно в искомый день, теряются. При поиске заездов на конкретную дату результат всегда неполный.
**Priority:** Medium

### Предусловия
- Создана бронь с `checkin=2031-06-15` (id далее — `{id}`).

### Шаги воспроизведения
1. Отправить `GET /booking?checkin=2031-06-15` — дата совпадает с датой заезда брони.
2. Проверить наличие `{id}` в выдаче.
3. Контроль: отправить `GET /booking?checkin=2031-06-14` и снова проверить.

### Ожидаемый результат (ОР)
Документация: «checkin date greater than **or equal to** the set checkin date». На шаге 1 бронь должна быть в выдаче.

### Фактический результат (ФР)
Шаг 1 — брони в выдаче нет. Шаг 3 — бронь есть. Сравнение выполняется как строгое `>` вместо `>=`.

### Вложения
Проверено на предзаполненных данных стенда: бронь id 1 имеет `checkin=2019-08-29`; запрос `GET /booking?checkin=2019-08-29` вернул 13 id, среди которых id 1 отсутствует.

### Воспроизводимость
100 % — 2 независимых прогона + 1 проверка в коллекции (TC-LST-11), контрольные TC-LST-12 и TC-LST-13 проходят.

## BUG-09 — POST /booking — `totalprice` не валидируется: отрицательный принимается, дробный молча усекается, `null` роняет сервер

**Окружение:** restful-booker, `https://restful-booker.herokuapp.com`, 29.08.2026
**Severity:** Major — денежное поле принимает бессмысленные значения и **теряет данные без предупреждения**: `99.99` превращается в `99`, то есть клиент недосчитывается копеек и никак об этом не узнаёт.
**Priority:** Medium

### Предусловия
- Стенд доступен.

### Шаги воспроизведения
1. Отправить `POST /booking` с `"totalprice": -50` — посмотреть сохранённое значение.
2. Отправить с `"totalprice": 99.99` — посмотреть сохранённое значение.
3. Отправить с `"totalprice": null` — посмотреть код ответа.
4. Отправить с `"totalprice": "111"` (строка) — посмотреть код ответа и тип в ответе.

### Ожидаемый результат (ОР)
1. `400 Bad Request` — отрицательная стоимость брони невозможна.
2. Сохранено ровно `99.99`, либо `400` с явным требованием целого значения. Молчаливое усечение недопустимо.
3. `400 Bad Request`.
4. `400 Bad Request` — документированный тип поля `Number`.

### Фактический результат (ФР)
1. `200 OK`, сохранено `-50`.
2. `200 OK`, сохранено `99` — дробная часть отброшена без предупреждения.

| `POST /booking` не требует авторизации: создать бронь может кто угодно | В документации эндпоинт описан как открытый. Это осознанное решение учебного стенда, а не отклонение от требований |
| `checkin` равен `checkout` (бронь на ноль ночей) принимается | Требуемое поведение в документации не описано; нужно решение о правиле |
| Верхняя граница длины строковых полей не задана: `firstname` из 5000 символов сохраняется целиком | Ограничение нигде не заявлено — сначала требование, потом дефект |
| Токен не имеет срока жизни и не отзывается: повторный `POST /auth` выдаёт **новый** токен, но **прежний продолжает действовать**. Проверено: токены `5deba69c6f3d33a` и `070fd3716e85353` одновременно дают `201` на `DELETE`. Токены накапливаются неограниченно | Ни срок жизни, ни правила отзыва в документации не описаны — отклонения от требований нет. Нужно решение аналитика: если отзыв предполагается, это дефект; если нет — требование к документации. Зафиксировано кейсами TC-AUTH-15, TC-AUTH-15a, TC-AUTH-15b |
| База стенда общая и периодически сбрасывается (за время работы id упали с 4450 до 80) | Штатное поведение бесплатного учебного стенда. Учтено в дизайне тестов: каждый кейс создаёт свои данные |
