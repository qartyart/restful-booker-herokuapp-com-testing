**Тестируемый сервис:** `https://restful-booker.herokuapp.com`
**Документация:** `https://restful-booker.herokuapp.com/apidoc/index.html` (снапшот — [api-spec.md](api-spec.md))
**Дата составления:** 29.08.2026
**Автор:** Аникеев Артём

Кейсы перенесены в Postman-коллекцию [`postman/restful-booker.postman_collection.json`](../postman/restful-booker.postman_collection.json), проверки — во вкладке Tests каждого запроса.

## Как читать

| Обозначение | Смысл |
|---|---|
| `{{base_url}}` | `https://restful-booker.herokuapp.com` |
| `{{token}}` | токен из `POST /auth`, кладётся в заголовок `Cookie: token={{token}}` |
| `{{bookingid}}` | id брони, созданной этим же прогоном |
| `{{tc_firstname}}` | уникальное имя вида `QaAuto1788021653`, генерируется в pre-request скрипте коллекции |
| `{{username}}` / `{{password}}` | учётные данные из документации API; Basic-заголовок собирается из них штатным блоком `auth`, а не задаётся литералом |
| **см. BUG-NN** | кейс вскрывает дефект; ОР написан **по документации**, фактическое поведение — в [bug-reports.md](bug-reports.md) |

**Про порог времени ответа.** Во всех кейсах он равен 5000 мс. Порог подтверждён замерами на 268 запросах: p50 = 537 мс, p95 = 623 мс, p99 = 657 мс — то есть он выше p99 более чем в семь раз и срабатывает только на реальном зависании, а не на обычном разбросе бесплатного Heroku-dyno.

**Важно про стенд.** База общая: её пишут все, кто проходит это задание, и она периодически сбрасывается (за время подготовки кейсов id упали с 4450 до 80). Поэтому ни один кейс не опирается на чужие данные, на бронь `id=1` и на абсолютные счётчики — каждый кейс создаёт собственную бронь с уникальным именем и работает только с ней.

## Диаграмма перехода состояний

REST сам по себе не хранит состояние сессии, но **ресурс** имеет жизненный цикл — его и моделируем. Ценность техники в том, что она заставляет проверить не только штатные переходы, но и **недопустимые**: те, о которых при линейном чтении спецификации не вспоминают.

### Жизненный цикл брони

```
                       POST /booking
   ┌───────────────┐  ───────────────►  ┌───────────────┐  ── PUT / PATCH (с токеном) ──┐
   │ НЕ СУЩЕСТВУЕТ │                    │  СУЩЕСТВУЕТ   │ ◄────────────────────────────┘
   └───────────────┘                    └───────┬───────┘
           ▲                                    │
           │                       DELETE (с токеном)
           │                                    ▼
           │                            ┌───────────────┐
           └────────────────────────────┤   УДАЛЕНА     │
                                        └───────────────┘
```

| Из состояния | Переход | Ожидаемый результат | Кейс | Факт |
|---|---|---|---|---|
| НЕ СУЩЕСТВУЕТ | `POST /booking` | `201`, состояние → СУЩЕСТВУЕТ | TC-CRE-01 | `200` без `Location` (BUG-15) |
| НЕ СУЩЕСТВУЕТ | `GET` | `404` | TC-GET-04 | соответствует |
| НЕ СУЩЕСТВУЕТ | `PUT` / `PATCH` / `DELETE` | `404` | TC-PUT-07, TC-PAT-07, TC-DEL-07 | `405` (BUG-13) |
| СУЩЕСТВУЕТ | `PUT` / `PATCH` с токеном | `200`, состояние не меняется | TC-PUT-01, TC-PAT-01 | соответствует |
| СУЩЕСТВУЕТ | `DELETE` с токеном | `200`/`204`, состояние → УДАЛЕНА | TC-DEL-01 | `201` (BUG-14) |
| СУЩЕСТВУЕТ | `PUT` / `PATCH` / `DELETE` без токена | `401`, состояние не меняется | TC-PUT-05, TC-PAT-05, TC-DEL-05 | `403` (BUG-12), состояние цело (TC-DEL-05a) |
| **УДАЛЕНА** | `GET` | `404` | TC-GET-08 | соответствует |
| **УДАЛЕНА** | `DELETE` повторно | `404`/`204` — DELETE идемпотентен | TC-DEL-08 | `405` (BUG-13) |
| **УДАЛЕНА** | `PUT` | `404` | **TC-PUT-13** | `405` (BUG-13) |
| **УДАЛЕНА** | `PATCH` | `404` | **TC-PAT-12** | `405` (BUG-13) |

Последние два перехода — вклад именно этой техники: состояния «удалена» и «никогда не существовала» различимы для клиента, и сервис обязан вести себя в них одинаково предсказуемо. Проверка показала, что **ведёт**: оба дают `405`. Нового дефекта нет, зато подтверждена консистентность — это тоже результат.

### Жизненный цикл токена

Именно этот переход был пропущен при разработке коллекции и сломал уборку: прогон получал токен в `00 Setup`, а к папке `99 Teardown` стенд успевал сбросить базу и обесценить токен. Лечится повторной авторизацией перед уборкой.

```
   ┌──────────────┐   POST /auth (валидные креды)   ┌──────────────┐
   │  НЕТ ТОКЕНА  │ ──────────────────────────────► │   ВАЛИДЕН    │
   └──────────────┘                                 └──────┬───────┘
          ▲                                                │
          │                                  сброс базы стенда
          │                                                ▼
          │                                         ┌──────────────┐
          └─────────────────────────────────────────┤  НЕВАЛИДЕН   │ → 403 на PUT/PATCH/DELETE
                                                    └──────────────┘
```

| Переход | Ожидаемый результат | Кейс |
|---|---|---|
| НЕТ ТОКЕНА → ВАЛИДЕН | `200` + `token` длиной 15 | TC-AUTH-01 |
| ВАЛИДЕН → используется в защищённой операции | операция выполняется | TC-AUTH-02 |
| ВАЛИДЕН → выдан ещё один токен | **прежний токен обязан быть отозван либо срок жизни задокументирован** | **TC-AUTH-15** |
| НЕВАЛИДЕН → защищённая операция | `401` | TC-PUT-06, TC-PAT-06, TC-DEL-06 |

## Причинно-следственный анализ

Техника выписывает условия входа (причины), наблюдаемые исходы (следствия) и связывает их логикой. В отличие от pairwise она не просто перебирает комбинации, а **объясняет** их — и позволяет находки не собирать, а выводить.

### Фильтры `GET /booking`

Причины: `C1` — задан `firstname`, `C2` — задан `lastname`, `C3` — задан `checkin`, `C4` — задан `checkout`.
Следствия: `E1` — своя бронь в выдаче, `E2` — пустая выдача, `E3` — код `500`.

| # | C1 | C2 | C3 | C4 | ОР | Факт | Кейс |
|---|---|---|---|---|---|---|---|
| 1 | — | — | — | — | весь список | соответствует | TC-LST-01 |
| 2 | ✓ | — | — | — | `E1` | соответствует | TC-LST-02 |
| 3 | — | ✓ | — | — | `E1` | соответствует | TC-LST-03 |
| 4 | ✓ | ✓ | — | — | `E1`, ровно одна запись | соответствует | TC-LST-04 |
| 5 | — | — | ✓ | — | `E1` при `checkin ≥` границы | граница исключена (BUG-06) | TC-LST-11…13 |
| 6 | — | — | — | ✓ | `E1` при `checkout ≥` границы | отбор инвертирован (BUG-03) | TC-LST-14, 15 |
| 7 | — | — | ✓ | ✓ | `E1` при выполнении обеих границ | всегда `E2` (BUG-04) | TC-LST-16, 17 |
| 8 | — | — | ✗ формат | — | `400` | `E3` — `500` (BUG-05) | TC-LST-18…20 |

**Вывод, который даёт именно эта техника.** Строка 7 не является самостоятельным дефектом — она вычисляется из строк 5 и 6:

```
C3 отбирает «строго позже границы»      (BUG-06)
C4 отбирает «не позже границы»          (BUG-03)
C3 ∧ C4 — пересечение по одной шкале дат пусто при любых значениях  →  BUG-04
```

Это меняет и порядок починки: исправление BUG-03 и BUG-06 закроет BUG-04 само.

### Авторизация защищённых методов

Причины: `A` — предъявлен валидный токен, `B` — ресурс существует. Следствие — код ответа.

| A (токен) | B (ресурс) | ОР | Факт | Кейс |
|---|---|---|---|---|
| ✓ | ✓ | `200`/`204` | `201` (BUG-14) | TC-DEL-01 |
| ✓ | ✗ | `404` | `405` (BUG-13) | TC-DEL-07 |
| ✗ | ✓ | `401` | `403` (BUG-12) | TC-DEL-05 |
| ✗ | ✗ | `401` | `403` | **TC-DEL-11** |

Четвёртая ячейка добавлена по результату анализа — без таблицы её легко не заметить. Результат **в пользу сервиса**: проверка авторизации выполняется раньше проверки существования, поэтому неавторизованный вызывающий не может по коду ответа выяснить, существует бронь или нет. Это корректная защита от information disclosure, и отсюда же следует уточнение к BUG-13: дефект проявляется только для авторизованных клиентов.

## Предугадывание ошибок

Техника, основанная на опыте (ISTQB, группа experience-based). Покрытия она не даёт и применяется поверх систематических техник, а не вместо них. Чтобы результат был воспроизводим, рядом с каждым кейсом зафиксирована **проверяемая гипотеза о реализации**.

| Гипотеза о реализации | Кейс | Результат |
|---|---|---|
| дата разбирается через `new Date()` без валидации, `String(NaN)` попадёт в хранилище | TC-CRE-21, TC-CRE-22 | в базе `0NaN-aN-aN` — **BUG-02** |
| дата разбирается «как получится», без сверки с форматом `CCYY-MM-DD` | TC-CRE-20 | `01-01-2026` молча стало `2026-01-01` — BUG-02 |
| денежное поле разбирается целочисленно | TC-CRE-14 | `99.99` → `99`, тихая потеря копеек — BUG-09 |
| проверки предметной области «выезд позже заезда» нет | TC-CRE-18, TC-PUT-12 | принимается — BUG-08 |
| строковые поля не санитизируются | TC-CRE-26 | `<script>` сохранён сырым — BUG-11 |
| приведение типов несимметрично | TC-CRE-12, TC-CRE-24 | строка→число даёт `200`, число→строка даёт `500` — BUG-10 |
| валидация схемы отсутствует, ошибку поймает рантайм | TC-CRE-05…10 | `500` вместо `400` — BUG-07 |

Семь гипотез — семь подтверждённых дефектов. Отдача выше, чем у систематических техник, по конкретной причине: те находят отклонения **от спецификации**, а здесь значительная часть дефектов лежит там, где спецификация молчит.
